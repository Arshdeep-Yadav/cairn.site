The reset problem

Every session starts from zero. Your project doesn't have to.

Claude Code, Cursor, Codex, Copilot — each one boots clean. So tradeoffs get relitigated, decisions get quietly reversed, and the reason a file looks the way it does disappears with the chat window.

Without shared memory

The project forgets

  1. A decision is made in chat.

    The reasoning, the rejected alternatives, the constraint that forced it.

  2. The chat closes.

    Only the code survives. The rationale does not.

  3. The next agent proposes the opposite.

    It has no way to know the question was already settled.

  4. Nobody remembers which one won.

    Or why. Or what would have to change for the old call to be right again.

With Cairn

The project remembers

  1. The decision is written once.

    Context, choice, why, alternatives, consequences — with an immutable id.

  2. Every agent reads it before acting.

    Accepted decisions are constraints, not suggestions.

  3. Changes link to the decision they implement.

    Files, commits, sessions, and agents all become edges in the graph.

  4. Superseded calls stay in the graph.

    Marked superseded, linked to the replacement, never silently erased.

Memory isn't a longer prompt.
It's a place.

A prompt is carried by one session. A vault outlives every session, every agent, and every model upgrade.

Cairn keeps one vault per project — or one across all of them — and gives each agent a small, standard interface to it. The memory is a folder of Markdown. The intelligence is in the links.

The working loop

Read. Work. Record. Hand off.

Cairn isn't a write-only log. It is a loop the agent runs every session: load what is already known, act on it, record what changed, and leave the next agent a clean starting point.

  1. 01

    Recall

    Load the project brief. Search before choosing an approach. Open the notes behind a decision before editing the file it governs.

    • memory_context
    • memory_search
    • memory_get
  2. 02

    Work

    Edit code as usual. Claude Code hooks append edits to a rolling worklog; git commits are captured with files, stats, and provenance. Diffs are not stored by default.

    • capture_changes
    • cairn capture-commit
  3. 03

    Record

    One idea per note. The title is a claim. The body carries the why, the alternatives rejected, and the consequences. Link it to what it implements or blocks.

    • memory_write
    • memory_update
    • memory_link
  4. 04

    Hand off

    Close with a summary and concrete next steps. Send a direct message or a structured handoff when another agent must continue without asking what happened.

    • memory_handoff
    • memory_send
    • memory_end_session

Why it holds The loop is installed as an always-on rule in the client, so the agent knows to read before acting and write while the context is still true. Skill-aware clients also get the long-form playbook.

Architecture

A folder of Markdown.
A graph in memory. Three ways in.

No database. No daemon required for the memory to exist. The vault is the truth; everything else is derived and disposable.

01

Nothing is locked in

Notes are Markdown with YAML frontmatter. Open the folder in Obsidian, grep it, diff it in git, edit it by hand. The app is a view, not a gatekeeper.

02

The index is disposable

No index files, no database migrations, no persisted caches. Restart the process and the graph is rebuilt from the notes that exist.

03

Three surfaces stay honest

The MCP server, the CLI, and the workspace all pass through one store, so a note written by an agent and a note written by the UI land identically.

Delete the index and you lose nothing.
Delete the vault and you lose the memory.

The memory model

Twelve kinds of note. Sixteen kinds of edge.

A note is a Markdown file with YAML frontmatter. Its kind selects the folder and the lifecycle. Its fields connect it to files, sessions, agents, and other notes — and those connections are the product.

Decision

proposed → accepted → rejected → superseded

A choice plus the why, the alternatives considered, and the consequences. One decision per note.

Change

active → committed → captured

What landed, where, and by whom. Files, stats, commit provenance, and links to the decisions it implements.

Insight

active → archived

How something actually behaves — the thing you learned by reading the code or running the test.

Question

open → answered

An unknown that blocks or shapes the work. Answers link back with an answers edge.

Answer

answered

The resolution to a question, kept as its own note so the question's history stays intact.

Spec

draft → active → archived

Behaviour another caller can rely on. The contract a later change must not quietly break.

Risk

open → mitigated → accepted

A hazard with a blast radius, not a vague worry. Include what breaks and who feels it.

Task

todo → doing → done → blocked

A promised follow-up that isn't done yet, visible to the next agent instead of buried in a summary.

Message

Direct or broadcast coordination. Unread state per agent.

Handoff

Structured work transfer: summary, next steps, open questions, files.

Session

Who worked, on what goal, with which model and client.

Note

The general-purpose kind when nothing more specific fits.

Edges agents write

Set in relations, or created with memory_link.

  • relates_toThe default connection
  • implementsA change makes a decision real
  • supportsEvidence for a claim
  • contradictsNew evidence against an old call
  • depends_onThis breaks if that changes
  • blocksA risk or question holds up a task
  • answersAn answer resolves a question
  • supersedesA newer call replaces an older one

Edges Cairn derives

Computed from fields, wikilinks, and provenance — no extra work for the agent.

  • touchesA wikilink to a file path
  • mentionsA wikilink to another note
  • part_ofNote → project node
  • authored_byNote → agent node
  • in_sessionNote → session node
  • addressed_toMessage → agent nodes
  • handoff_toHandoff → recipient
  • replies_toMessage threading

## Context
Every request currently crosses the region to reach one
central limiter. At peak, that hop is pure added latency.

## Decision
Keep the token bucket in the edge worker. Rejected the
central Redis bucket: one more network dependency on the
hot path, and a shared failure domain.

## Consequences
Per-edge counters can drift. Reconcile on a schedule and
link the follow-up spec.
01

Identity and lifecycle

id is immutable and ULID-ish. kind selects the folder and the status machine. The title is the graph label — make it a claim, not a category.

02

The graph fields

related, relations, supersedes, and files create typed edges. Wikilinks in the body create touches and mentions. aliases keep Obsidian wikilinks resolving.

03

Provenance

project, agent, session, and created record who wrote this and when. metadata carries structured payload such as a commit sha or branch.

04

Safe writes

dedupe_key turns a repeated write into an upsert. Redaction runs first, then an atomic write. Deletion is lazy, so the graph never dangles.

Everything is hand-editable except id. If you can edit a Markdown file, you can extend the memory.

The MCP surface

Fourteen tools. Two resources.
Zero ceremony.

Cairn runs as a local MCP stdio server using the official SDK. One instance per agent: --agent stamps every write, --project scopes it, and the session id links everything written in between.

Before work

Read

Call memory_context. Search the topic, file, or error before choosing an approach.

While working

Write

Record one idea per note as it becomes true. Link it. Capture the change set after edits.

Before stopping

Hand off

Close the session with a summary, next steps, and anything the next agent must not rediscover.

Read

6 tools

Cheap, read-only calls. Safe to make often; designed to be the first thing an agent does.

Cairn read tools
ToolWhat it returnsCall it when
memory_context The living brief: decisions in force, proposals, open questions, risks, recent changes, handoffs, unread messages, active agents, and high-context files. An optional focus appends a targeted search. First call in a task, or when switching projects.
memory_search Ranked results with snippets and ids across titles, bodies, tags, files, projects, and agents. Filter by kind, status, tags, or recency; search one project or all of them. Before choosing an approach, and before writing, to avoid a near-duplicate.
memory_get One note with its full body, typed relations, links out, backlinks, files, session, and related notes. After search or context surfaces an id worth reading in full.
memory_graph JSON {nodes, edges, stats} around seed notes or a query, depth 1–4. Optional file and agent nodes. Virtual project, agent, session, and file nodes have ids. Impact analysis: what implements, depends on, blocks, touches, or supersedes something.
memory_timeline Recent activity, newest first and grouped by day. Filter by project, agent, kind, and lookback window. Catching up after time away, or building a handoff.
memory_inbox Unread messages and handoffs addressed to you, plus broadcasts. Optionally include closed handoffs. When the brief shows unread items. Set mark_read once handled.

Write

4 tools

Durable changes. Every write is redacted, linked, and serialized against other processes.

Cairn write tools
ToolWhat it returnsCall it when
memory_write A new note with kind, title, body, status, tags, files, related ids, typed relations, recipients, session, dedupe key, and metadata. Files auto-link to related notes. A decision, insight, risk, question, spec, task, or change becomes true.
memory_update Append or replace a body; change status, tags, files, relations, or metadata. Append is the default, so outcomes accumulate safely. An outcome arrives, a question is answered, or a decision is superseded.
memory_link A typed edge between two notes: relates_to, implements, supports, contradicts, depends_on, blocks, answers, supersedes. A change implements a decision, a risk blocks a task, or an answer resolves a question.
capture_changes The git change set as change memory: files, stats, commit provenance, and automatic links to related decisions. Identical captures deduplicate. Diffs are omitted by default. After edits or a commit. Use a manual change note when there is no git repo.

Coordinate

4 tools

Sessions and agent-to-agent traffic. This is what makes memory collaborative instead of a personal notebook.

Cairn coordination tools
ToolWhat it returnsCall it when
memory_start_session Registers the session, marks the agent online, and returns the project brief. Reuses a recent active session when one exists. Later writes on the connection link to it automatically. At the start of substantial work, with a concrete goal.

Install

Install once. Then two commands.

Node 20.19 or newer. The npm names cairn and cairn-memory belong to unrelated packages, so Cairn installs directly from its GitHub source. Run the launch and wiring commands from your project root; Cairn creates .cairn/ if it doesn't exist. Setup is idempotent, and existing client files are backed up before Cairn edits them.

Before you start node --version→v20.19 or newer npm available (npm --version) Git optional — only capture_changes commit scope needs it
  1. 01

    Install the CLI

    Pick your shell. The installer checks Node, builds from source once, and puts a cairn command on your PATH. It never touches your vault. npm 12 blocks dependency install scripts and the npm names are taken, so npx cairn is not used.

    Launch

    First run creates the vault, starts the workspace, and prints a one-time password. Replace it at the first login — the generated password cannot open a lasting session.

    $ cairn
  3. 03

    Wire a client

    Writes the MCP entry, the always-on rule, and — where supported — the skill and hooks. Add several clients in one command.

The workspace

The graph is the point.

Cairn ships a no-build web app for seeing what your agents know: a force-directed graph, a living brief, the timeline, inboxes, handoffs, agent presence, and project scopes. It updates over SSE the moment another agent writes.

Living brief

Decisions in force, attention items, recent commits, and online agents — the same brief the MCP server returns.

Graph canvas

Force layout with collision-culled labels, kind filters, search highlighting, and an inspector for links and backlinks.

Timeline

Every note grouped by day, filterable by agent or kind. The fastest way to catch up after time away.

Coordination

Inboxes, handoff boards, unread counts, and live agent presence. Work changes hands without a transcript.

Omnibox and capture

⌘K or Ctrl K searches and navigates. N captures a note from anywhere in the app.

Live, local, themeable

SSE pushes refreshes in place. Light, dark, or system. No external fonts, scripts, or CDNs; no build step.

The workspace is served from the same Node process as the API. Run cairn ui --open to launch it directly, or let cairn do both.

Security & ownership

Local by default.
Yours by construction.

The workspace and API are password-gated and bound to loopback. The memory is plain Markdown on your disk. No account, no telemetry, no hosted copy.

One folder to back up

The vault is the whole product. Copy it, sync it, version it, or move it to another machine. Cairn rebuilds everything else.

.cairn/
├── cairn.config.json      name · project · settings
├── README.md              generated orientation
├── notes/
│   ├── decisions/         2026-11-17-decision-…md
│   ├── changes/
│   ├── questions/
│   └── …                  one folder per kind
└── state/
    ├── auth.json          scrypt hash + secret · 0600
    ├── .write.lock        cross-process lock
    ├── sessions/
    ├── inbox/
    └── backups/           redacted client files · max 40
cairn auth status cairn auth reset CAIRN_NEW_PASSWORD=… cairn auth set-password

Reset and set-password rotate the session secret, signing out every browser. The first-run generated password cannot open a lasting session; the login page forces a replacement.

  • Back upCopy .cairn/. No database dump, no export step.
  • ShareHand a teammate the folder. The files already make sense.
  • InspectOpen it in Obsidian, grep it, or diff it in git.
  • LeaveDelete the folder. No remote copy remains.

Password by default

The UI and API require a session. Passwords are salted scrypt hashes with 64-byte keys; the session secret never leaves state/auth.json. Only health, login, auth status, and login assets are public.

Hardened sessions

HMAC-signed HttpOnly, SameSite=Strict cookies with a 12-hour TTL and an in-memory server-side allowlist. Logout, reset, or restart revokes immediately. Failed logins are throttled per client address.

Request guards

Host is parsed and allowlisted before URL handling. Mutations require JSON content type, an allowed Origin, Sec-Fetch-Site, and a session-bound double-submit CSRF token.

Redaction at the boundary

Titles, bodies, backups, and requested diffs are scanned for private keys, cloud and API token shapes, and password= / api_key= / token= assignments before they land.

Capture filters

.env*, credential stores, key files, dependency and build directories, lockfiles, binary media, and the vault itself are skipped. Diffs are omitted unless explicitly requested; captures record what changed, never the patch body.

Files and concurrency

Writes are atomic (temp file + rename) with 0600 files and 0700 directories on POSIX. A reentrant cross-process lock is shared by MCP, CLI, and UI. Backups are redacted, capped at 40, and private.

The boundary, stated plainly

A security page that hides its limits isn't one. These are the parts Cairn does not pretend to solve.

  • MCP is outside the web password. It is a stdio process launched by your coding client. It runs as your OS user and reads/writes the vault directly.
  • The memory is plaintext on disk. Anyone with filesystem access can read it. There is one shared workspace password, no per-user accounts, and no audit log.
  • Redaction is best effort. It is pattern-based, not a guarantee. redact: false in the vault config turns it off.
  • Remote access needs a proxy. Set CAIRN_ALLOWED_HOSTS, terminate TLS in front, set CAIRN_SECURE_COOKIE=1, and pass --allow-remote. Never port-forward the raw HTTP port.

Run it on a laptop.
Or a team server.

Cairn is one Node process with a folder for state. The Docker image is multi-arch, runs as an unprivileged user, and expects TLS in front when you expose it.

Docker, one command

docker run -d \ -p 4242:4242 \ -v cairn_data:/data \ -e CAIRN_ALLOWED_HOSTS="cairn.example.com" \ -e CAIRN_PASSWORD="YourSecurePasswordHere" \ --name cairn \ ghcr.io/arshdeep-yadav/cairn:latest

The image starts with --host 0.0.0.0 --allow-remote, stores the vault at /data/.cairn, and probes /api/health. Add CAIRN_SECURE_COOKIE=1 once HTTPS is in front.

  • TLS in frontCaddy, Fly, or your load balancer terminates HTTPS. Cairn speaks plain HTTP on 4242.
  • Allowlist the hostSet CAIRN_ALLOWED_HOSTS to the exact public hostname — not a wildcard.
  • Keep the volume/data holds the entire memory. Without it, the container starts empty.
  • Never publish raw HTTPNo direct port-forward, no public 4242. Put a proxy and a password in front.

Architecture MCP reference Full README
Why doesn’t npx cairn work?

Because the npm names cairn and cairn-memory belong to unrelated packages, and npm 12 blocks dependency install scripts. On macOS or Linux run curl -fsSL https://raw.githubusercontent.com/Arshdeep-Yadav/Cairn/main/install.sh | sh; on Windows run irm https://raw.githubusercontent.com/Arshdeep-Yadav/Cairn/main/install.ps1 | iex in PowerShell. Either installer builds locally and installs a tarball, so no npm publishing is involved.

Is Cairn a database?

No. A vault is a folder of Markdown files with YAML frontmatter. Cairn builds an in-memory graph index at startup and throws it away on exit. There are no migrations, no index files to corrupt, and no lock-in.

Does anything leave my machine?

No. Cairn has no telemetry, no hosted service, and no external fonts, scripts, or CDNs. The workspace binds to 127.0.0.1 by default. If you deploy the container yourself, the data goes wherever you put the volume.

What happens when two agents write at once?

Read-modify-write operations take a reentrant cross-process lock at state/.write.lock, shared by the MCP server, the CLI, and the UI. Individual writes are atomic: temp file, then rename. On POSIX, files are 0600.

Can I open the vault in Obsidian or edit notes by hand?

Yes. The folder is plain Markdown. Wikilinks and aliases keep Obsidian links resolving, and frontmatter fields create the graph edges. Everything is editable except id, which the graph uses as identity.

Do I need git?

Only for commit capture. capture_changes and the post-commit hook read git; without a repository, agents can still write change notes manually with a files list. The rest of Cairn is independent of git.

Can one vault serve multiple repositories?

Yes. Initialize a global vault with --global at ~/.cairn/, point each client at it, and pass --project <name> in the server entry. Notes carry their project scope, and tools can search across all projects.

What happens if I delete a note others link to?

The note disappears; a missing placeholder node stays so the graph never has a dangling reference. Backlinks and the inspector show the gap instead of silently rewriting history.

How is this different from a long context window or a CLAUDE.md file?

Those live with one session or one repository and are rewritten wholesale. Cairn is queryable, append-only by default, shared across agents, and typed: a decision can link to the change that implements it and the risk that blocks it. Context is supplied; memory is maintained.

Which clients are supported?

Claude Code, Cursor, Antigravity, VS Code / GitHub Copilot, Codex, Gemini CLI, Windsurf, Zed, OpenCode, Omnirush, and any MCP client that accepts a stdio command. Four are configured automatically; the rest print a snippet.

What is the license and current version?

MIT. The current release is 0.1.0, requires Node 20.19 or newer, and ships with no native binaries.
